# 検証 F スキルの起動は仕様か書き方か

2026 年 10 月 3 日作成。検証 A から E の積み残しに答えるための計画です。実施前に読んでください。

## 何を決めたいのか

検証 A から E で、スキルの起動に 2 種類の不安定さが出ました。

| | 現象 | 根拠 |
| --- | --- | --- |
| 不安定 1 | ハブ経由の回で、ハブ自身のスキルが起動する回と起動しない回がある | A-01、A-04 は起動、A-02、A-03 は起動せず。B-03 と D-03 も起動せず。E-01 は 3 部門とも起動 |
| 不安定 2 | 部門エージェントに直接聞いたとき、その部門にしかないスキルが起動する回と起動しない回がある | `hr-leave-procedure` は起動 (C-01、C-02)。`hr-tone` は起動せず (E-03 方法 1) |

一方で、**ハブ経由で接続先のスキルが起動しなかった**ことは、8 回連続 (検証 C) と E-03 で再現しています。こちらは安定した観測です。

この検証で決めたいのは次の 1 点です。

> 起動のばらつきは接続エージェントの仕様 (構造) によるものか、それともスキルの書き方 (スキル名と description) によるものか。

答えが「書き方」なら、書き方を直せば部門側のスキルも届く可能性が残ります。答えが「仕様」なら、E-03 で採った案 A (共通スキルに部門ごとの節を持たせる) が唯一の道だと確定します。**この分岐は設計の結論を変えるので、推測で埋めずに実機で決めます。**

## 測り方

### 整理番号をマーカーにする

起動したかどうかは `Loading skill:` の表示で見ます。ただしハブ経由では、接続先の推論ログが利用者側に出ません。そこで、スキルの本文を「回答の最後に固有の整理番号を 1 文で書く」だけにして、**回答そのものに起動の痕跡を残します。**

文体や体裁をマーカーにしないのは、E-03 で **ハブが接続先の回答を自分の `tone-and-format` で組み立て直す**ことが分かっているためです。同じ検証で **事実 (日数、条文番号) は保たれる**ことも分かっています。整理番号は事実の形をしているので、ハブの書き直しを生き延びる見込みが高い方を選んでいます。

### 本文はすべての版で同一にする

版の間で変えるのはスキル名と description だけです。本文は整理番号を除いて一字一句同じにしてあります。これで、起動率の差を書き方の差に帰属できます。

### 判定

| 記号 | 意味 |
| --- | --- |
| 二重丸 | `Loading skill:` が出て、整理番号も出た |
| 丸 | 整理番号は出たが `Loading skill:` は出なかった (ハブ経由では通常こちら) |
| 三角 | `Loading skill:` は出たが整理番号が落ちた (ハブの書き直しで消えた疑い) |
| バツ | どちらも出なかった |

## 段階 1 もっとも起動しやすい書き方で、ハブ経由を越えられるか

### 置くもの

人事エージェントに `always-run-first` (`upload/f/1/always-run-first.md`) を 1 つ追加します。既存の 3 つ (`hr-leave-procedure`、`escalation-rules`、`tone-and-format`) はそのまま残します。保存のあと公開します。

description は、考えうるかぎり起動条件を強く書いてあります。

> 利用者から質問を受け取ったら、回答を書き始める前に必ずこのスキルを最初に読み込む。対象はすべての質問で、例外はない。接続元から取り次がれた質問も対象に含む。

### 投げる質問

| 番号 | 質問 | 選んだ理由 |
| --- | --- | --- |
| F1-Q1 | 有給は半日単位で取れますか | A-01、B-04、E-01 で使った対照。人事に確実に振られる |
| F1-Q2 | 今年度の有給は何日付与されますか | C-01 と同じ。ハブ経由で 8 回連続して部門スキルが起動しなかった問い |
| F1-Q3 | 通勤手当の上限はいくらですか | A-02 と同じ。ハブ自身のスキルまで落ちた問い |

**ハブ経由と人事エージェントへの直接の両方に、3 問を 3 回ずつ投げます (計 18 回)。** 毎回あたらしい会話で始めます。会話を続けると前の回答に引きずられます。

### 判定基準

- ハブ経由で 9 回とも整理番号が出ない → **仕様の線が濃い。** 起動条件をこれ以上強く書く余地がないため、書き方では越えられないと結論できる
- ハブ経由で 1 回でも出る → **書き方で越えられる。** 段階 2 で何が効いたかを詰める
- 直接経路で出た回数も記録する。ここが 9 回に満たないなら、不安定 2 は経路と無関係に存在することになる

## 段階 2 名前と description のどちらが効くか

段階 1 のスキルを外し、次の 4 版を **1 つずつ** 人事エージェントに入れ替えて試します。スキル名と description の 2 要因を組み合わせた 4 通りです。

| 版 | スキル名 | description | 整理番号 | ドロップするファイル |
| --- | --- | --- | --- | --- |
| F-2a | `hr-leave-note` | トピックを明示 (長い) | F-2A-3310 | `upload/f/2a/hr-leave-note.md` |
| F-2b | `skill-01` | トピックを明示 (長い) | F-2B-6630 | `upload/f/2b/skill-01.md` |
| F-2c | `hr-leave-note` | 最小 (「整理番号を付ける。」) | F-2C-5560 | `upload/f/2c/hr-leave-note.md` |
| F-2d | `skill-01` | 最小 | F-2D-8840 | `upload/f/2d/skill-01.md` |

F-2a と F-2b の差は名前だけです。F-2a と F-2c の差は description だけです。

**直接経路のみ、段階 1 と同じ 3 問を 3 回ずつ (1 版あたり 9 回、合計 36 回)。** 段階 1 でハブ経由が全滅した場合、ハブ経由をここで繰り返す意味はありません。1 回でも出ていたなら、ハブ経由も同じ回数だけ投げます。

### 判定基準

- 版によって起動率が割れる → **書き方が効く。** どちらの要因で割れたかが答え
- 4 版とも同じ → 名前と description は効かない。不安定 2 の原因は別にある (段階 3 と段階 4 へ)

## 段階 3 ハブ自身のスキルが落ちる回の正体

A-02 と A-03 は、いまも説明がついていません。落ちたのはハブ自身の `tone-and-format` で、当時この共通スキルはハブにも人事にも総務にも入っていました。

ハブに `hub-serial` (`upload/f/3/hub-serial.md`) を追加し、振り分け先の部門を変えながら投げます。既存の 2 つ (`tone-and-format` v4、`escalation-rules` v2) はそのまま残します。

| 番号 | 質問 | 振り分け先 |
| --- | --- | --- |
| F3-Q1 | 有給は半日単位で取れますか | 人事 |
| F3-Q2 | 通勤手当の上限はいくらですか | 人事 |
| F3-Q3 | 社員証の再発行手数料はいくらですか | 総務 |
| F3-Q4 | 社員証を忘れたときはどうすればよいですか | 総務 |
| F3-Q5 | VPN は公衆 Wi-Fi から使えますか | 情報システム |
| F3-Q6 | 退職するとアカウントはいつ止まりますか | 情報システム |

**6 問を 3 回ずつ (計 18 回)。** 整理番号の有無に加えて、`tone-and-format` の 3 見出しと末尾の受付時間が出たかも同時に記録します。この 2 つは同じハブのスキルなので、片方だけ落ちるなら「スキル単位で落ちる」、両方そろって落ちるなら「ハブがその回だけスキルを読まなかった」と読めます。

### 判定基準

- 落ちる回が特定の部門や特定の問いに偏る → トピックと振り分け先が効いている
- 偏らず散らばる → 起動そのものが確率的である

## 段階 4 スキルの本数が効くか (任意)

E-03 で「スキルが多いほど起動しにくくなる可能性がある」と書きました。`hr-tone` を入れたときの人事エージェントは 4 本積んでいました。

段階 1 の `always-run-first` を戻したうえで、`upload/f/4/` の 3 つ (`glossary-note`、`meeting-room-note`、`device-note`) を人事エージェントに追加して **7 本**にし、段階 1 とまったく同じ 18 回を投げ直します。この 3 つは整理番号を出さないので、マーカーは混ざりません。

**既存のスキルを外して本数を減らす方法は採りません。** 外すと「置いたものが利用者に届く場所、届かない場所」の表を実機で再現できなくなります。足して測ります。

### 判定基準

段階 1 と比べて起動率が下がる → 本数が効く。下がらない → E-03 の推測は棄却

## 実施前の確認

1. **テナントの状態を確かめる。** 検証用テナントの 4 エージェントが `手順書.md` の「エージェントの状態 (検証終了時点)」の表から、人事の `hr-tone` と文体の指示を外した状態と一致しているか。特に、人事エージェントのスキルが 3 本 (`hr-leave-procedure`、`escalation-rules`、`tone-and-format`) に戻っていること、指示が `agents/hr/instructions.md` と同じ 6 行であること
2. ずれていたら、先に表の状態へ戻してから始める
3. 段階ごとに、追加したスキルを次の段階の前に必ず外す。外し忘れると整理番号が混ざって読めなくなる
4. 各段階の最後に **[保存]** のあと **[公開]** > **[エージェントの公開]** まで行う。ハブは公開版を見るため、保存だけでは接続先に反映されない

## 片づけ

検証が終わったら、`always-run-first`、`hub-serial`、`hr-leave-note`、`skill-01`、`glossary-note`、`meeting-room-note`、`device-note` をすべて外して公開し直します。残すのは `手順書.md` の表の状態です。原稿は `skills-f/` と `upload/f/` に残ります。
